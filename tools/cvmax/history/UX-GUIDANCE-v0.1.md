# CvMax 状态告知与分步引导规范 v0.1

日期：2026-09-05。来源：用户明确提出的体验原则。状态：设计规范，尚未实现。

## 1. 四项硬要求

1. 业务有边界：明确操作对象、授权范围、完成条件、暂停条件、终止条件及不能保证的外部结果。
2. 状态可理解：用户能知道最近确认发生了什么、当前是否仍在执行、下一步由谁完成。
3. 引导逐步展开：先给简短路径，再只展开当前一步；用户完成或系统确认成功后再给下一步。
4. 助手主动执行：已有授权且能独立完成的操作由助手直接做，简短告知即可；不能把内部诊断、规则选择等工作转嫁给用户。

## 2. 当前状态的统一表达

一条状态最多呈现四个核心信息：

- 对象：公司/岗位；批次时附当前岗位及整体进度。
- 事实：最近确认完成了什么、当前阻塞是什么。
- 主责：助手处理中 / 等你操作 / 已停止 / 待你检查。
- 下一步：一个主操作，或明确“你暂时无需操作”。

例：“星河科技 · 前端工程师：已保存填写记录，等待网页登录。现在请你完成登录，我会检测后继续。”

“已保存记录”不等于“招聘网站已保存草稿”；“前端核验通过”不等于“申请已提交”。不得用统称“处理中”掩盖等待用户、连接断开或执行已终止。

状态带 revision、最近确认时间、更新来源及连接新鲜度。断线立即标注“连接已断开，以下为最后确认状态”，不能把缓存结果当实时事实。更新恢复时按版本合并，较晚到达的旧通知不能覆盖新状态。

执行状态、验证状态和后续责任分开：例如执行已结束但还有两项必填未解决，应显示“部分填写完成，2 项需要你处理”，不能是绿色完成。

## 3. 业务边界与停止语义

| 状态 | 判定 | 对用户说明 | 允许后续 |
|---|---|---|---|
| 填写中 | 正在执行已授权的动作 | 当前阶段；无需操作 | 暂停/停止 |
| 等你操作 | 缺事实、登录、个人决定或手动控件处理 | 一个当前动作及保留成果 | 完成后核验继续 |
| 等待页面/服务 | 有具体等待条件及有限自动预算 | 正在等什么；用户暂不操作 | 成功继续；耗尽后给恢复入口 |
| 已暂停 | 用户要求或可恢复的外部条件 | 原因、影响范围、最后确认成果 | 用户暂停只由用户解除 |
| 需要重新核对 | 动作结果/页面状态不确定 | 哪些结果尚未确认 | 先观察，不能盲重试 |
| 待检查提交 | 到达最终复核边界且必填已解决 | 填写完成，尚未提交 | 用户原页检查提交 |
| 部分完成 | 无法完成剩余项，但成果可交付 | 已做/未做、原因、下一入口 | 手动处理或新尝试 |
| 已停止 | 用户终止执行 | 不再派发动作；已开始动作可能有结果待核对 | 不自动复活；重新开始是新执行 |
| 无法继续 | 页面关闭岗位、能力不支持或预算耗尽等 | 具体原因及可保留内容 | 合理的人工替代或结束 |

停止的作用域必须可见：当前申请 / 整个委托。暂停与停止不是同义词。最终提交、登录账号授权、验证码等边界不因重试或学习而扩张。

网站已有数据不能保证撤销。停止后若有已派发动作未返回，显示“已停止后续操作，正在核对最后一步”，核对只读；无法核对就保留未知状态，不能宣称全部已撤销。

系统等待条件必须具体、有自动等待预算；耗尽即离开无限加载态。等待用户可跨会话持久存在，不因时间流逝视为用户已同意/已完成。等待记录的保留期和到期处置须可见，到期不自动删除简历或网站内容。

## 4. 分步引导协议

开始解决一个问题时，用一句话说明目标，并给最多三个阶段词，例如“打开登录页 → 完成登录 → 返回填写”。复杂过程按阶段分组，不把十条技术操作塞入三个长段。

随后仅展开当前阶段：一个主动作、必要位置提示、成功判据；后面的步骤默认折叠。可提供“查看完整步骤”，但不能默认倾倒全部操作。

阶段由谁负责必须明确：

- 助手阶段：“我先检查连接，你暂时不用操作。”随后直接执行，不能再次问是否检查。
- 用户阶段：“请在已打开的窗口中完成登录。”等待页面证据或用户回报；“收到”“好的”不作为完成证据。
- 自动核验阶段：用户说已完成后重新观察，确认成功再推进，避免仅凭文字强制跳转。

当前步失败就在当前步提供一个更具体的恢复动作，不重复整个长教程。路线变化时用一句话解释变化并更新概览。成功后如下一步由助手完成，直接做，不要求用户点击无意义的“下一步”。

用户可以随时停止、返回或提问；保留阶段与上下文。用户跨入口回来的第一句应是“上次停在 X，现在需要 Y”，而不是重新解释产品。

## 5. 登录引导示例

初次阻塞：

“星河科技需要先登录。接下来：打开页面 → 你来登录 → 我继续填写。”

助手可定位时：“我已打开对应页面。现在请完成登录，密码直接在网站输入。”

无法自动打开时只显示当前动作：“请点击‘打开登录页’。”不要同时列账号注册、邮箱验证、验证码、返回路径等尚未发生的步骤。

若出现二次验证：“现在需要输入网站发给你的验证码。请在网站完成，我继续等你。”不索取验证码。

确认后：“登录已完成，我正在重新检查表单并继续填写，你暂时无需操作。”

检测不确定：“还没有确认登录成功。请检查网站是否已经回到申请表单；完成后点击‘重新检查’。”按钮不是无条件恢复执行。

## 6. 问答与通知负担

收集用户事实与排除技术故障采用不同策略：同一页面已发现的短问题可以集中成一个小表单；多步骤故障修复始终只展开当前步骤。大批量缺失问题分组，不因“集中提问”让用户填写另一份巨型表单。

默认只提醒有意义的阶段变化、必要用户动作、完成和失败。用户正在相关页时优先页内提示；跨入口只保留一个主要提醒，其他界面同步状态，不多处刷屏。

完成反馈简短：“已填写 3 个岗位，等待你检查提交。”可展开逐岗详情。每项下一步要直达正确页面，不给泛泛的“请重试”。

## 7. 模拟评审与实际验证的区分

独立 agent 情境推演发现的是设计缺口及风险假设。必须有文档依据和具体触发情境；已有规则不能被误报为缺失。该方法不能证明真实用户满意度、控件可操作性、无障碍合规或端到端成功率，之后仍需可交互原型与真实测试。


## 8. 本轮已明确的具体策略

- 首发安装边界：复用已有可用 Atoll/agent；应用可诊断并启动自己的服务，不安装、升级或修复 Atoll 核心。缺少前置环境时显示“尚未开始填写”，保存岗位入口，只给当前安装/连接步骤和稍后继续。不存在支持路径时明确暂不能使用，不能循环重试。
- 最小准备：确认姓名、联系邮箱和当前要用的附件即可进入申请流程；其他事实按申请需要补充。解析失败保留原附件与已提取草稿，不强迫整份重录。目标页面需要其他必填事实时仍必须补齐。
- 仅切换浏览器焦点不暂停；执行 tab 导航到不同上下文才废弃定位并暂停。普通编辑不等于显式接管：先保护编辑字段并自动只读重验；显式接管暂停自动写入，等用户继续。
- 人工停止在申请记录上保留禁止自动触发标记；刷新、重开、复制 tab、登录成功均不得解除。暂停入口叫“继续”，停止入口叫“重新开始”；新执行仍继承该申请的累计尝试预算。
- 登录只检查可见账号信息，不读取密码或凭证。可见账号与用户指定目标明确冲突时先停下引导换号；无法确认且可能涉及账号归属时，仅针对当前登录会话询问一次“是否为本次申请使用的账号”，仍须核验表单和岗位上下文。
- “先跳过”将岗位留在待办，处理其余已授权岗位，不在本批结束后自动绕回。关闭岗位/用户明确取消单项是该项终止，告知后继续其他已授权项；不视为需要用户处理的阻塞，也不擅自替换岗位。
- 批次收尾逐项归账，计数守恒。例如“1 项待检查，1 项已关闭，1 项已取消；助手已结束处理”。待办仍有未决项时必须明确，不用“全部完成”。
- 附件按申请绑定；用户明确指定“美国岗用英文版、国内岗用中文版”即执行，只对不确定项提问。开始回执及复核页可查看各岗位资料/附件版本，不能所有岗位强行使用默认简历。
- 答案范围与保存期限分开：默认“仅这份申请”，可明确选“用于本批这些岗位”及“保存到长期资料”。仅本次答案进入申请覆盖值，不创建长期 ProfileVersion；只有选择长期保存才生成资料版本。临时覆盖值默认 30 天到期，可提前清除；仍未完成的任务到期后标明需重新补充。应用留存与 Atoll 账本/模型记录的边界就近说明，不能承诺全链路不留存。
- 恢复默认由助手重开并核验原岗位，只把登录/身份歧义/资料选择交给用户。“上次验证 18 项”与“当前网页已验证项”分开展示。未留存的网页手填值不能承诺恢复。
- 资料切换显示版本时间、附件及受影响字段；仅在当前申请/用户指定范围切换，其他申请维持原版本。前页或附件仍未重验时不得显示整份完成。
- 自动尝试按 Application 累计，Run/重启不重置额度。继续前展示剩余预算；增加预算需明确追加范围，已停止任务不会因充值额度或登录恢复自行开工。
- 停止/接管先阻止新动作并标记在途目标。确认无旧写入的字段才能声明可安全修改；未确认目标保持提示。停止后只读核验默认最多 30 秒，不能确认则结束自动检查，标“结果未知”和网站定位入口；不自动重传附件或重新点击新增。


## 9. 学习反馈、无障碍与故障出口

学习状态使用准确标签：已记录候选、验证通过、已隔离、已禁用。一次成功不称“已学会”，验证通过也不承诺所有未来页面都适用。展开详情包含方法类型、适用场景和验证记录，不把个人校名/答案展示成通用知识。

禁用/撤销经验后的收据分别说明：停用哪些版本、未来是否复用、当前字段是否仍需修复、个人资料是否改变。停用错误经验不等于修复网页；受影响字段先撤销旧通过状态，核验/修复后才重新完成。

能力不支持时，追加时间或次数不是解决方法；只给当前可用的人工处理或结束路径。预算耗尽但仍有可行策略时，说明追加后会尝试什么，由用户决定是否继续。任何不能继续的状态都应给明确的当前责任与终止出口。

状态变化需可被屏幕阅读器感知：必要中断、恢复、完成播报岗位、状态及下一步；不逐字段播报，不随意抢焦点。跨 tab 定位后说明当前岗位、目标字段及错误；返回助手保留原焦点位置。定位目标失效先由助手重定位，失败后才给一个具体人工动作。以上是待实现和实测的无障碍要求，不能据文字设计声称已合规。

## 10. 验收断言

- 任一可见状态都能回答“哪个岗位、最近确认什么、现在谁负责、下一步做什么”。
- 断线时显示最后确认时间；旧 revision 的回执不能让停止任务重新变成填写中。
- 三个依赖同时失败时只展示一个当前主动作，先修上游，后续自动重检。
- 用户说“好的”不推进需要事实完成的步骤；用户说“做完了”触发核验，不能无条件进入执行。
- 助手能检查连接、定位网页、读取上传状态时直接做，不要求用户重复承担这些操作。
- 暂停/停止/部分完成/待检查的文案、主按钮、后台行为一致；停止后无自动写入复活。
- 在途动作无法核验时在有界时间后结束自动检查，保留未知结果与人工定位入口。
- 仅本申请答案不修改长期资料；跨岗位使用范围和留存范围分别可见。
- 恢复显示历史成果与当前网页核验两套口径，空白草稿不冒充已恢复。
- 每条经验纠正都有范围收据，不把规则停用冒充网页已改正。
- 问题概览不超过三个简短阶段，当前只展开一个人工步骤；阶段改变时更新概览。
