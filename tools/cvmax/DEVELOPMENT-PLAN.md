# CvMax 产品与开发总计划 v2.0

日期：2026-09-06
工作分支：`codex/job-application-autofill`

## 1. 阶段关系

CvMax 的产品边界已经确定，当前进入应用层开发。开发仍按以下门禁推进：

```text
P 产品设计 → T 技术可行性验证 → E 工程设计 → I 正式开发 → R 发布验收
```

现有 `src/` 和 `extension/` 按最新版边界逐项审计后使用；普通自动化测试位于 `test/`。每项功能都必须证明其复用 Atoll 公开能力。若需要 Atoll 核心为业务让步，该项立即停止。

## 2. 产品前提

CvMax 是 Atoll 的业务应用，沿用 Atoll 的身份、频道、消息、Agent、MCP 工具和生命周期，不建立绕开 Atoll 的第二套平台。

一期当前实现用户已有 AI 桌面中的 Skill/Client/CLI 入口。Atoll Web 保留入口设计，等后续阶段再实现；它不能成为当前交付声明。所有宿主接入同一个 Atoll 内部服务，共享 taskId、资料快照、问题、申请结果和经验。

一期覆盖三个场景：当前页面、单个岗位链接、用户确认后的多个岗位链接。多岗位严格串行。系统只填写和核验，最终提交永远由用户完成。资料中心、商业账号、岗位推荐数据、支付和后台管理属于二期。

## 3. P：产品设计阶段（已完成）

目标：不依赖正式代码，把入口、完整流程、安装体验、异常交接、状态表达和业务边界设计清楚，并通过 10 个独立用户角色验证。

### P0 产品关系与范围

明确 CvMax 与 Atoll 的关系，一期/二期范围，以及 Web、外部 AI、内部 Agent、应用服务、Chrome 插件的职责。明确最终提交、敏感资料、登录和验证码边界。

出口：每项功能都能归属到 Atoll 原有能力或 CvMax 应用组件，不存在为业务方便而绕开系统设计的功能。

### P1 用户、入口和场景矩阵

设计三条当前主路径，并为未来 Web 保留同契约位置：

| 入口 | 当前页面 | 单链接 | 多链接 |
|---|---|---|---|
| 外部 AI Skill | 当前页委托 | 链接委托 | 清单确认后委托 |
| Atoll Web（未来） | 复用同一契约 | 复用同一契约 | 复用同一契约 |

每条路径写清发起条件、资料来源、用户授权、处理中反馈、人工参与点、跨入口接续和结束状态。

出口：三条当前路径端到端完整；入口差异和场景差异没有混淆；外部 AI 不承担第二套页面执行循环。

### P2 核心流程与状态体验

原型必须覆盖：

1. 任务建立前：连接状态、目标页面、资料范围和“不最终提交”。
2. 处理中：最多三个短阶段，只展开当前一步；持续显示最新确认事实和当前负责人。
3. 用户交接：登录、验证码、敏感字段、缺失事实、已有值冲突和站点不支持。
4. 控制：暂停、恢复、跳过当前岗位、停止整个任务。
5. 异常：页面效果未知时先核对，不自动重填。
6. 完成：逐岗位显示 `ready_for_review`、`partial`、`skipped`、`failed` 或 `cancelled`；Task 完成不能误导为全部岗位成功。

每个等待状态只告诉用户当前需要做的一步，后续步骤只显示简短阶段名。

出口：每个状态都有进入条件、可执行动作、下一步负责人和终止条件。

### P3 安装与首次使用原型

这里设计的是安装体验，不是开发安装器。原型覆盖：

- 创建或选择私有 CvMax 频道。
- 安装 Skill/CLI。
- 安装 Chrome 插件并一次性说明招聘页面访问范围；任务中没有逐站授权步骤。
- 插件与当前 CvMax 服务配对。
- doctor 检查 Atoll 身份、频道、Agent、应用服务、插件和当前页面。
- 首次任务、权限失败、浏览器未连接和卸载流程。

出口：新用户仅靠原型提示就能理解需要安装什么、为什么、当前完成到哪一步、失败后如何恢复；不要求理解 MCP、Actor 或内部调度。

### P4 三端产品原型

历史原型展示同一个任务的三个界面，用于产品设计验证：

- Atoll 原生 Web：委托、附件、问题、状态和停止。
- 外部 AI：Skill 引导、资料准备、委托、查询和回答。
- Chrome 插件：连接、当前岗位、最近确认状态、定位页面、暂停和紧急停止。

覆盖正常流程、登录、缺资料、已有值、未知结果、批量部分完成和用户停止。原型只模拟产品交互，不声称技术已经实现。

出口：三端使用同一个 taskId 和一致状态；用户不重复输入同一信息；插件没有独立业务规划和最终提交能力。

### P5 十个独立用户角色模拟

重新启动 10 个独立角色验证最新原型；旧版本模拟不能替代本轮。角色覆盖：首次安装者、只用 Web、只用外部 AI、当前页快速填写、批量投递、需要登录、简历缺项、敏感字段谨慎用户、无障碍/低熟练用户、页面变化后的再次使用者。

每个角色独立完成：理解入口 → 建立任务 → 遇到问题 → 处理或停止 → 判断最终状态。记录卡住步骤、状态误解、缺少出口、一次给出过多指导、下一步负责人不清楚和边界不可信。

出口：10 份独立记录完整；高优先级问题完成设计修复；使用相同角色脚本复验。

### P6 产品设计冻结

交付产品定义、三条当前主旅程、未来入口约束、异常分支、状态与终止条件、安装流程、原型、10 角色首轮与复验报告、产品验收标准。

上述材料和十角色问题清单已经完成；范围调整后，Web 原型只保留未来入口设计，不作为当前开发验收项。

## 4. T：技术可行性验证阶段

目标：产品设计冻结后，用最小、可丢弃的实验验证“能否按 Atoll 的设计实现”。它不验证产品体验，也不形成生产代码承诺。

当前范围验证五个问题：

1. 外部宿主读取的本次文件，能否以私有、有期限引用交给服务。
2. 内部 Agent 能否通过标准工具发现和调用 CvMax MCP，且不借用人类凭证。
3. Skill/CLI 是否使用现有 principal、频道和同一 taskId。
4. 应用服务能否把受限动作交给 Chrome 插件，并获得页面证据。
5. 停止、断线、迟到回执和重启时，能否阻止自动重放并如实报告未知结果。

最小流程使用一个合成页面、一个非敏感字段、一次 Client 委托、一次插件填值、一次页面回读和一次停止/故障测试。完整流程再覆盖真实简历、招聘站点、重复经历和经验系统。

出口：五个问题都有通过、失败或架构阻塞结论；若必须修改未授权核心流程，停止对应方案并返回产品设计调整。

当前事实：五项均已在应用层实现和回归；未知页面效果保持只读核对，未要求新的核心改动。

## 5. E：工程设计阶段

将冻结的产品设计和已验证能力转成开发规格：组件与部署拓扑、领域模型、数据 schema、公共命令、内部 Agent 工具、Chrome 插件协议、幂等与恢复、权限与隐私、测试计划和垂直开发切片。

出口：每个产品交互都有状态和接口承载，每个异常都有恢复策略，没有未解决的核心改动依赖。

## 6. I：正式开发阶段

P、T、E 已通过，以下切片均已完成当前应用范围：

- I1 产品骨架：应用服务、Atoll 装配、CLI/Skill、Chrome 插件连接与诊断。
- I2 单岗位闭环：当前页/单链接、完整表单、附件、人工交接、停止和核验结果。
- I3 多岗位串行：冻结清单、逐岗结果、跳过、持久接续和跨入口接续。
- I4 经验与自进化：候选、验证、有限复用、漂移、隔离、纠正和回退。
- I5 产品化：安装升级、插件弹窗、宿主适配和卸载。

每个切片同时完成代码、测试、用户可见状态、错误出口和文档。

## 7. R：发布验收阶段

发布阶段只验证实现是否符合冻结设计，不再承担产品方向探索。当前仓库完成本地安装、权限和 secret 检查、三场景契约回归、真实授权网站经 CvMax 产品插件验证及已知限制；签名、分发和生产多站点矩阵在独立发布工程完成。

Codex/ChatGPT 浏览器控制只能辅助观察，不能替代 CvMax Chrome 插件证据。

## 8. 停止条件

以下情况停止受影响路径并返回上一阶段：产品原型无法说明状态或终止条件；10 角色仍有高优先级问题；技术方案要求修改未授权 Atoll 核心；无法阻止最终提交、后续动作或未知操作重放；真实资料、凭证或跨用户答案可能进入发布包或共享经验。

## 9. 当前状态

公共经验权威存储已确定为 CvMax 应用自有 MySQL，并已完成独立数据库、五表迁移、最小权限账号、Registry API、签名发布、TTL 缓存、持久离线队列、匿名反馈和跨安装复用。当前已证明 candidate → canary → released 与失败自动 suspended；后续发布工程需补齐显式回滚、密钥轮换、限流和独立安装凭据。Atoll 核心数据库与调度逻辑保持不变。

当前阶段：`R 发布准备`。

当前范围已经交付唯一 CvMax Skill、Client/CLI、内部 Agent、应用服务、Chrome 插件和经验闭环。Web 入口暂不实现。代码继续服从 Atoll 已有身份、频道、消息、Agent、工具桥和生命周期；需要核心妥协时停止该项。
