# 用户10：多申请完成状态推演

仅据 PRODUCT-DESIGN.md（P）与 USER-JOURNEYS.md（J）独立推演，非实际测试。角色：多入口管理申请，关注完成、责任方和通知有效性。

## 七步推演

1. 委托甲乙丙丁，看到“填写后由你提交”；无需逐项启动。
2. 甲到最终复核边界：读到“待检查提交”，理解尚未提交，接下来由我检查。
3. 乙缺必填许可信息，我选择暂不回答：应保留“待补充”，明确整份未完成；我选择“先跳过这个岗位”后才处理丙。
4. 丙岗位关闭：看到关闭原因、停止处理且不替换；不再占待办或计入成功。
5. 丁预算耗尽后又断线：需要知道已停及保存结果；恢复连接不应自行追加预算。
6. 从甲侧栏切列表，在网页修改一项再回对话：列表和任务卡应改为“需重验”；旧“填写完成”通知不能让我误以为当前仍通过。
7. 回看四份：甲需重验、乙待我补充、丙已关闭、丁待恢复/预算决定；不能称“完成4份”或一直“处理中”。

## 设计问题

1. **高｜批次结束与单份阶段缺少组合规则。** J54规定分类结果，J111遇人工处理暂停委托，P128–130仅列Run状态。混合结局时不清楚助手还会不会继续。验收：汇总区分执行已停与申请未提交，列出各类数量、未开始项及下一责任方；关闭项有明确结局。
2. **高｜旧通知的失效呈现未定义。** P98将消息定义为当时收据，J124要求修改后重验，J128只规定通知去重。用户可能点旧完成通知作判断。验收：延迟完成通知晚于需重验到达时，不覆盖新状态；打开后显示当前结果、核验时间和旧通知已过期。
3. **中｜预算与断线叠加后的当前动作不清。** P215有重试上限和显式加预算，J105仅给重试入口。用户可能反复点重试却毫无进展。验收：保留两种阻塞，先恢复连接再核验，仍需额外预算才单独请求决定；达到策略上限不重复同一尝试。
4. **中｜集中问题未限制展开负担。** P41、J109集中询问，未约定当前一步和完成条件。跨岗位待办可能一次铺满。验收：短概览至多三步，仅展开当前问题；用户操作经核验完成才推进。

## 渐进示例

“先恢复连接 → 核验草稿 → 处理剩余项。现在我先检查连接。”检查失败才展示一个用户修复动作；修复确认后助手重验。若预算仍不足，再问是否增加明确额度，不同时堆出三个操作。
