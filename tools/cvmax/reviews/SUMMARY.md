> 范围更新：本报告与冻结基线为历史评审证据。当前一期已收敛为 Codex + Skill + CLI，推荐工作台等退出一期；本次整理没有重新运行 10 个角色，也不把旧结论当成新版验收。有效需求见 [当前设计](../README.md)。

日期：2026-09-05。评审对象：PRODUCT-DESIGN.md v0.2 与 USER-JOURNEYS.md v0.1。

## 方法和边界

按用户要求启动 10 个独立 agent；并发上限为 3 个子 agent，因此分批运行，每个角色独立阅读同一设计基线，不读取其他报告或本轮新增规范。每人输出角色旅程、最多四项问题、原文行号、改善建议与验收条件。

这是设计情境推演，不是真实用户研究、可操作原型测试或软件端到端验证。没有实际登录、填写或提交任何岗位。36 条原始角色观察归并为下列 10 类设计问题；重复观察不是独立故障数，也不能转换成用户比例或成功率。

原始行号对应 [baseline/PRODUCT-DESIGN.md](baseline/PRODUCT-DESIGN.md) 与 [baseline/USER-JOURNEYS.md](baseline/USER-JOURNEYS.md)，哈希记录在 baseline/manifest.json。此后的设计修订不改变基线证据。

## 总体判断

原设计已有三个入口、资料隔离、恢复重扫、经验隔离及最终提交边界，不能将这些误报为完全缺失。主要不足在状态交接及用户可观察契约：后台机制存在，但用户未必知道当前是否仍在工作、该由谁处理、如何退出，以及当前提示是否仍然有效。

核心路径在文字层面可以串联，但尚不能断言流畅可用。发布前必须将以下规则实现为可观察行为并做实际测试；不需要通过本轮模拟去修改 Atoll 核心。

## 归并问题与决策

P1 表示上线前必须明确并验收；P2 表示应随主流程一起完善。严重性是设计风险排序，不是已经证实的软件故障。

| 问题 | 来源 | 决策与验收重点 |
|---|---|---|
| P1 首次使用的前置条件和最小准备不清 | 01 | 明确首版复用已有 Atoll；缺失时标申请未开始，保留入口。先修当前依赖；确认姓名/邮箱/附件可进入，其他按需补充 |
| P1 缺少统一渐进引导协议 | 01/02/05/08/10 | 至多三个短阶段概览，只展开当前人工步骤；明确负责人、完成证据与失败出口。能自己做的检查/定位直接做 |
| P1 旧进度和当前状态可能被混用 | 02/06/09/10 | 显示 revision、最后确认时间及新鲜度；区分历史已填与当前核验；旧通知不能覆盖新状态 |
| P1 暂停、停止、接管的边界未贯通 | 02/07/08 | 停止标记阻止刷新/登录/自动模式复活；在途目标单列；有界只读核对后以已确认/未知收尾 |
| P1 恢复、预算和能力边界交接不明 | 06/09/10 | 助手先恢复连接、核验网页；按申请累计预算，不能重启刷新；能力不足不靠加次数解决，多重阻塞逐步处理 |
| P1 登录恢复未覆盖账号归属和反复失败出口 | 03 | 可见账号冲突时暂停；身份不明确时针对当前会话确认，不收密码；核验失败说明原因，给定位/跳过/停止路径 |
| P1 多岗位范围变更与终态汇总不完整 | 03/04/10 | 已选清单可随时查看；跳过保留待办；关闭/取消单项终止并继续余项；批次分项计数，明确助手是否结束 |
| P1 “仅本次”与长期资料存在文本歧义 | 05/06 | 默认仅这份申请的覆盖值，长期保存才升资料版本；批次复用另选范围；附件逐岗绑定，切版本显示受影响项 |
| P1 学习变化与网页修复没有明确区分 | 09 | 候选/验证/隔离准确标识；撤销给范围收据；停用规则不表示网页已修正，受影响字段重验后才完成 |
| P2 非视觉状态与跨窗口引导缺少验收契约 | 08 | 必要状态播报且不抢焦点；定位后说明岗位/字段；返回保留焦点，失效目标由助手先重定位 |

## 已落入本轮设计的改进

新增 [UX-GUIDANCE.md](../UX-GUIDANCE.md)，明确四项原则、状态表达、终止语义、分步引导、登录示例、通知负担、具体策略及验收断言。两份原设计同步引用并修正直接冲突的条款。

三项核心口径：

1. 状态必须回答“哪个岗位、最近确认什么、现在谁负责、下一步是什么”。离线时只能显示最后确认状态。
2. 故障处理先给简短路线，再只展开当前一步；用户说“好的”不等于完成，用户说完成则触发核验。
3. 自动填写完成、部分完成、等待用户、人工停止、网站提交是不同事实，按钮和后台行为必须一致。

## 建议的后续实测

将当前设计做成可交互原型后，优先验证三个高风险交接：首次连接失败后的分步修复、SSO 登录后的恢复、在途上传时停止与接管。每次记录用户能否独立回答“发生了什么、下一步谁做、怎样结束”。

真实评测不能用本轮 agent 的对话示例替代用户观察；也不能因十个角色都提交报告就宣称设计已通过上线验收。
